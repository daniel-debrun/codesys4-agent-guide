# 03: The CODESYS 4 text-folder project format

CODESYS 4 stores a project as a folder of plain text files. Git diffs them like any source tree, and you can
edit them with a normal editor. This page describes a **device project** (`*.fbsdev`) as created by the
v1.0.0.0 UI for CODESYS Control for Linux SL 4.22, and as extended by hand for the bench line. All file
contents below are real.

## Kinds of project folders

Suffixes found in the `WorkspaceManager` assembly and the UI bundle [tested by `strings`/`grep`]:

| Suffix | What | Status |
|---|---|---|
| `Name.fbsdev/` | device project (a PLC with its applications) | [tested] |
| `Name.fbslib/` | library project | [unverified] (seen in help and examples only) |
| `Name.fbsws` | workspace (the UI's "Create Workspace") | [unverified] (seen in UI code only) |
| `X.iecapp` + `X.iecapp^/` | an application inside a device project | [tested] |

The UI's "Create Device Project" dialog asks for a path, a project name, a title and a version, which must be
3- or 4-part semver [observed]. The **path field wants a `file://` URL** ending in `/`. A plain path failed
with `Parent path must be a directory: '/home/dev/c4work'`, while `file:///home/dev/c4work/` worked
[tested]. Then "Add PLC" lists the device descriptions, and "Add Program" creates `PLC_PRG`.

## Layout of a device project

What the UI generated (the Add Program step included), and what the build adds [tested]:

```text
BenchLine.fbsdev/
├── ProjectInfo.json                  hand-editable   {"version": "1.0.0"}
├── Communication.settings.json       hand-editable   used for online (gateway) connections only
├── Devices/
│   ├── DeviceTree.json               hand-editable   device name + identification + children
│   ├── BenchPLC.device.json          hand-editable   device identification + PLC settings
│   └── .devDesc-cache/4102/0000 0005/4.22.0.0/device.devdesc.xml   GENERATED (copy of the device description)
├── Application.iecapp                hand-editable   the file contains just: {}
├── Application.iecapp^/              the application's contents
│   ├── PLC_PRG.prg.st                source
│   ├── TaskConfiguration.json        source
│   ├── Libraries.json                source (library references)
│   ├── Libraries.lock.json           GENERATED by `c4-cli library install`, but commit it (pins versions + sha384)
│   ├── .intermediate/GDM.lock.json   GENERATED (the device model the compiler sees)
│   ├── .compileContexts/C4Project.<Project>.<App>.<guid>.compileinfo   GENERATED
│   └── .bootapp/Application.app, Application.crc                     GENERATED by `bootapp compile`
└── .library-cache/<Vendor>/<Library>/<ver>/<Library>.compiled-library GENERATED by `library install`
```

- **Generated folders can be deleted.** A copy of the bench project without `.bootapp/`, `.intermediate/`,
  `.compileContexts/`, `.library-cache/` and `Devices/.devDesc-cache/` built with 0 errors [tested]. The
  `.gitignore` used:

  ```gitignore
  .bootapp/
  .intermediate/
  .compileContexts/
  .library-cache/
  .devDesc-cache/
  CODESYS-4/
  ```
  (`CODESYS-4/` covers the stray `CODESYS-4/managed-libraries` directory that the relative default repository
  path creates in the current directory; see `docs/08`.)
- **Sub-folders inside `Application.iecapp^/` are free-form.** The bench used `Sim/`, `Comm/` and `Safety/`,
  and every POU in them compiled and ran [tested].
- The build names the application `<ProjectFolderName>.<AppName>`, for example
  `------ Build started: Application: BenchLine.Application -------` [tested]. We did not test renaming
  the `.fbsdev` folder, the device or the application after creation [unverified].
- A hand-made folder with a wrong layout (a *directory* named `App.iecapp` and no device files) failed at
  compile with `Error: Cannot find node (file:///tmp/t1/Bench.fbsdev/App.iecapp^/) in object model (Parameter 'path')`
  [observed]. The same kind of run once hung; see `docs/08`.

## File by file

### `ProjectInfo.json` [tested]

```json
{
	"version": "1.0.0"
}
```

The UI's dialog also has a "Title" field. The agent tried adding `"title"` and reverted it without building,
so that key is [unverified]. For libraries, `c4-cli library save-compiled` reads the semver version and its
prerelease and build labels from this file [unverified, from help text].

### `Communication.settings.json` [tested]

```json
{
	"device": {
		"nodeName": null
	},
	"gateway": null
}
```

Left at these nulls, because deployment copied boot-application files and never used the online
connection [tested]. The vendor help describes filling it through a "Communication Settings" wizard (add a
gateway, pick the controller, create the first runtime user) for IDE download and login [unverified].

### `Application.iecapp` [tested]

```json
{}
```

It is a **file**, not a directory. The application's content lives in `Application.iecapp^/`.

### `Application.iecapp^/TaskConfiguration.json` [tested]

As generated:

```json
{
	"taskGroups": [
		{
			"groupName": "IEC-Tasks",
			"tasks": {
				"DefaultTask": {
					"calls": [
						"PLC_PRG"
					],
					"priority": 1,
					"type": "Cyclic",
					"interval": 200000,
					"watchdogEnable": false,
					"watchdogTime": 0,
					"watchdogSensitivity": 0
				}
			},
			"coreConfig": "FixedPinned"
		}
	],
	"systemEvents": []
}
```

The bench changed `"calls"` to `["Safety_Interlock", "PLC_PRG", "MqttComm"]` and `"interval"` to `10000`, and
that built and ran [tested].
- `interval` is most likely in **microseconds** (200000 = 200 ms, 10000 = 10 ms) [unverified: the bench's
  design did not depend on the scan period, so this was never measured].
- We assume `calls` run in list order within one cycle [unverified].
- Errors in this file are reported as `Error parsing TaskConfiguration '{TaskConfig}': {Message}. Please fix the file.`
  and there is a JSON schema embedded in the compiler assembly (`TaskConfigurationSchema.json`) [observed
  in DLL strings; never triggered].

### `Application.iecapp^/Libraries.json` [tested]

As generated:

```json
{
    "references": {
        "Standard": {
            "$type": "Placeholder",
            "placeholder": "Standard"
        } 
    },
    "placeholderOverrides": {}
}
```

Final bench version. It built and ran, with a managed (version-pinned) library whose global names are
visible without a prefix:

```json
{
	"references": {
		"Standard": {
			"$type": "Placeholder",
			"placeholder": "Standard"
		},
		"SysSocket": {
			"$type": "ManagedLibrary",
			"libraryId": "SysSocket, 3.5.19 (System)",
			"allowUnqualifiedAccess": true
		}
	},
	"placeholderOverrides": {},
	"libraryParameters": {}
}
```

An earlier version, which also built and ran, used a placeholder reference under a namespace:
`"MQTT": {"$type": "Placeholder", "placeholder": "MQTT_Client_SL"}`. The code then used names such as
`MQTT.MQTTClient` [tested].

- The key under `references` (`"Standard"`, `"MQTT"`, `"SysSocket"`) is the **namespace** you use in code.
- `$type` values seen: `Placeholder`, `ManagedLibrary` [tested]. The lock file also shows `CompiledLibrary`
  [tested]. Relative-path references come from `library set-relative` [unverified].
- Other keys offered by the `set-*` commands: `optional`, `publishSymbolsInContainer`, `includePrerelease`,
  `linkAllContent`, `defaultResolution` [unverified: from `--help`, not tried].

### `Application.iecapp^/Libraries.lock.json` [tested]

Written by `c4-cli library install`, and it is large: 815 lines and 89 `$type` entries for the bench. It
pins each resolved library with a relative path into the project's cache and a SHA-384 hash:

```json
{
	"resolutions": {
		"3SLicense, 3.5.22 (CODESYS)": {
			"$type": "CompiledLibrary",
			"path": "../.library-cache/CODESYS/3SLicense/3.5.22/3SLicense.compiled-library",
			"sha384": "A27DAF831239DE243A509ABE8D455FB89654D53865C18916BE0BA5116D693A40F9A3D7BEAF095530310D735DEDBE850C",
			"allowUnqualifiedAccessByLibrary": true,
			"references": {
				"CAA Types Extern, 3.5.17 (CAA Technical Workgroup)": {
					"sources": {
						"CAA": {
							"$type": "Placeholder",
							"defaultResolution": "CAA Types Extern, >=0.0.0 (CAA Technical Workgroup)",
							"resolverGuid": "b303f5ce-75ff-4668-a777-7da8debb449c",
							"placeholder": "CAA Types",
							"allowUnqualifiedAccess": true
						}
					}
				},
```

- Spaces in paths are URL-encoded (`../.library-cache/System/Base%20Interfaces/3.5.17/…`) [tested].
- The device adds implicit references. `_3S_LICENSE`, resolved from placeholder `3SLicense`, shows up even
  though `Libraries.json` lists only `Standard` [tested].
- The bench committed this file. When the libraries changed (MQTT Client SL was swapped for SysSocket), the
  agent deleted the old lock file and ran `library install`, which wrote a new one [tested]. We did not test
  whether `install` updates a stale lock file in place [unverified]; `library resolve --all` exists for that
  [unverified, help text]. If the lock file is missing, `install-managed` complains
  (`Libraries.lock.json does not exist. You must resolve your libraries first.`) until a plain `install` has
  run [tested].

### POU and GVL source files [tested]

| Extension | Kind | Template the UI writes |
|---|---|---|
| `Name.prg.st` | PROGRAM | `PROGRAM Name` / `VAR` / `END_VAR` / `// implementation here...` / `END_PROGRAM` |
| `Name.fn.st` | FUNCTION | `FUNCTION Name : <type>` … `END_FUNCTION` (the bench wrote these by hand) |
| `Name.fb.st` | FUNCTION_BLOCK | `FUNCTION_BLOCK [PUBLIC] [FINAL] [ABSTRACT] Name [EXTENDS …] [IMPLEMENTS …]` + `VAR_INPUT`/`VAR_OUTPUT`/`VAR` blocks + `END_FUNCTION_BLOCK` [unverified: from UI code, not compiled] |
| `Name.gvl` | global variable list, as a **namespace** | `{attribute 'qualified_only'}` / `NAMESPACE Name` / `VAR_GLOBAL` / `END_VAR` / `END_NAMESPACE` |
| `.meth.st`, `.prop.st`, `.itf` | method, property, interface | [unverified: extensions from UI code only] |
| DUT (struct, enum, union, alias) | exists in the UI ("Add DUT"); file extension not found | [unverified] |

A real function from the bench (`Sim/Rng_Uniform.fn.st`); comments above the `FUNCTION` line are fine:

```iecst
// xorshift32; a value in (0, 1). Each station owns separate streams, like lineloop.sim.
FUNCTION Rng_Uniform : LREAL
VAR_IN_OUT
    State : UDINT;
END_VAR

State := State XOR SHL(State, 13);
State := State XOR SHR(State, 17);
State := State XOR SHL(State, 5);
Rng_Uniform := (UDINT_TO_LREAL(State) + 0.5) / 4294967296.0;

END_FUNCTION
```

A real GVL (excerpt of `GVL_Comm.gvl`), accessed from code as `GVL_Comm.Head`, `GVL_Comm.QSIZE` and so on:

```iecst
{attribute 'qualified_only'}
NAMESPACE GVL_Comm
// Outgoing MQTT queue (ring buffer) shared by the line logic and MqttComm.
VAR_GLOBAL CONSTANT
    QSIZE : INT := 1024;
END_VAR
VAR_GLOBAL
    BrokerHost : STRING(64) := '127.0.0.1';
    BrokerPort : UINT := 1883;
    Head : INT;          // next message to send
    Tail : INT;          // next free slot
END_VAR
END_NAMESPACE
```

**Languages.** For any language other than ST, the UI's program generator wraps the body in
`__BEGIN_IMPLEMENTATION('<LANG>')` … `__END_IMPLEMENTATION` inside the same file. The only language
identifiers found in the UI bundle are `"ST"` and `"LD"`, and the `CODESYS.C4.Ladder.Ext` extension (component
version 0.1.0.0) is installed [observed]. We only wrote ST. Whether v1.0 supports exactly ST and LD, and what
an LD file looks like, is [unverified].

## What the UI's JSON-RPC does (for the curious)

The UI talks to its session over a WebSocket. Workspace methods in the bundle include `CreateWorkspace`,
`OpenWorkspace`, `CreateDeviceProject`, `CreateLibraryProject`, `CreateApplication`, `AddTaskConfiguration`
and `AddProjectInfo` [observed]. No CLI exposes these. Driving the UI headlessly with Playwright worked for the
one-time skeleton creation [tested]; calling the RPC directly was not tried.
