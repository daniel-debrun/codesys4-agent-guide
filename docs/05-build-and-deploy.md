# 05: From a source edit to a verified program on the soft PLC

This is the workflow that worked on 2026-09-30, automated in the bench project's `orchestrate/plc.py`
(Python, run as root on the machine that hosts both the IDE and the runtime). It ran end to end three times
(apply 125 s, revert 111 s, one manual deploy) and in dozens of build-only runs [tested].

```text
0. one-time setup  → 1. edit source → 2. copy to a build dir → 3. library install → 4. bootapp compile
→ 5. back up the running app → 6. stop runtime → 7. copy .app/.crc → 8. start runtime
→ 9. wait ~60 s → 10. read back and compare → (restore on failure)
```

## 0. One-time setup

1. **The build user.** Use a non-root Linux user in group `codesys-4` (here `dev`); see `docs/01` [tested].
2. **An absolute library repository path** for that user [tested]:
   ```bash
   su - dev -c 'mkdir -p ~/CODESYS-4/managed-libraries ~/.config/CODESYS-4 && cat > ~/.config/CODESYS-4/LibraryRepositories.prefs.json <<EOF
   {
   	"localRepositories": {
   		"Default": "/home/dev/CODESYS-4/managed-libraries"
   	}
   }
   EOF'
   ```
   Without this, resolution fails: `Could not resolve the reference for the library with namespace Standard: Placeholder resolution for 'Standard' (defined by extension CODESYS.C4.GlobalLibraries.Ext.) to 'Standard, 3.5.22 (System)': Library not found in repositories.`
   The system libraries are found even though this repository stays empty. The extensions under
   `/opt/codesys-4/extensions` supply them, and the relative path only broke the repository setup as a whole
   [tested]. The file may not exist until a CODESYS session or command has run once as that user.
3. **A project skeleton.** Take one of these:
   - Copy `examples/minimal/Minimal.fbsdev` (JSON files as generated by the UI) [tested content, see its README].
   - Or create it in the UI once: Menu → Create Device Project (path as a `file:///…/` URL, name, version
     `1.0.0.0`) → Add PLC → "CODESYS Control for Linux SL" → name it → Add Program → Structured Text → Create
     [tested, driven headlessly with Playwright, see "Headless UI" below].
4. **The runtime's boot-app config** (root): `/etc/codesyscontrol/CODESYSControl_User.cfg`, section `[CmpApp]`,
   must contain `Application.1=Application` [tested as present; see `docs/02`].

## 1-2. Edit, then build in a scratch copy

Edit the files under `Application.iecapp^/` (see `docs/03`). Build from a copy, not the source tree. That
keeps generated files out of git, gives the build user its own files, and leaves a pristine source to roll
back to [tested]:

```bash
work=/home/dev/build/$TAG/BenchLine.fbsdev
rm -rf "$(dirname "$work")"; mkdir -p "$(dirname "$work")"
rsync -a --exclude .bootapp --exclude .intermediate --exclude .compileContexts --exclude .library-cache \
      ./BenchLine.fbsdev/ "$work/"
chown -R dev:dev /home/dev/build
```

## 3-4. Resolve libraries and compile (as the build user)

```bash
app="$work/Application.iecapp"
su - dev -c "c4-cli library install '$app' -v"        # success text: "Finished processing N libraries."
su - dev -c "c4-cli bootapp compile '$app' -v"         # success text: "BootApp finished"
ls "$work/Application.iecapp^/.bootapp/"               # Application.app  Application.crc
```

How `plc.py` decides whether the build succeeded [tested]:
- Run each step up to twice, and stop retrying once its success text appears. `library install` sometimes
  segfaults on exit after it has finished.
- The **last** line that starts with `Build complete` must contain ` 0 errors`, and
  `.bootapp/Application.app` must exist. Otherwise the build failed. Keep the full log for the error lines
  (format: `docs/09`).
- `examples/scripts/c4-build.sh` does the same in bash.

Time: `library install` + `bootapp compile` for the bench took about 25 s in total. In the audit log one apply
went from planned to built in 37 s, and that includes copying and checks [observed].

## 5-8. Deploy the boot application (as root)

```bash
RT=/var/opt/codesys/PlcLogic/Application
bak=/home/dev/build/backups/$(date +%Y%m%d-%H%M%S); mkdir -p "$bak"
cp -p "$RT"/Application.app "$RT"/Application.crc "$bak"/ 2>/dev/null || true      # 5. backup

grep -q '^Application.1=Application' /etc/codesyscontrol/CODESYSControl_User.cfg || \
  sed -i 's/^\[CmpApp\]$/[CmpApp]\nApplication.1=Application/' /etc/codesyscontrol/CODESYSControl_User.cfg

for p in $(pgrep -f '^/opt/codesys/bin/codesyscontrol.bin'); do kill "$p"; done   # 6. stop
for i in $(seq 60); do pgrep -f '^/opt/codesys/bin/codesyscontrol.bin' >/dev/null || break; sleep 1; done

mkdir -p "$RT"                                                                      # 7. install
cp "$work/Application.iecapp^/.bootapp/Application.app" "$work/Application.iecapp^/.bootapp/Application.crc" "$RT/"
chown -R codesyscontrol:codesyscontrol "$RT"

/usr/local/bin/start-softplc                                                        # 8. start (docs/02)
```

The same steps as a script: `examples/scripts/deploy-bootapp.sh`. On a systemd host, steps 6 and 8 would be
`systemctl stop/start codesyscontrol` [unverified here: no systemd in the container].

What we never did: log in and download from the IDE ("Download Application", gateway, runtime user). The
vendor help describes that path; it is [unverified] on Linux.

## 9. Wait for the application to run

Check the runtime log for these lines [tested]:

```text
Bootproject of application [<app>Application</app>] load started ...
Application [<app>Application</app>] loaded via [Bootproject]
Application [<app>Application</app>] started
```

Without CodeMeter they appear about 60 s after the start, because the runtime first waits
`CmRuntime could not be connected within 60[s]`. In the bench, the program's first MQTT message came
56-62 s after `start-softplc` [tested, at least 6 times]. Poll; do not sleep a fixed time:

```bash
for i in $(seq 60); do
  timeout 2 mosquitto_sub -h 127.0.0.1 -t plant/bench/heartbeat -C 1 >/dev/null 2>&1 && { echo "up after ~$((i*2)) s"; break; }
done
```

## 10. Verify by read-back

The program state is not observable from outside by default: there is no symbol configuration in 1.0, and
the IDE's online monitoring was not used. So the bench program **publishes its own parameters**, as retained
MQTT topics every 5 s. Each payload carries a build tag that the deploy tool writes into the source
[tested]:

```text
plant/bench/params/weld {"build":"cr-study09-weld","WeldCycle_ms":49500.0,"WeldCv":1.0e-1,...}
```

The verifier waits (up to 240 s) until **every** params group reports the new build tag and each edited
variable equals its new value (relative tolerance 1e-9). Only then does it declare success. A retained
message from the old program cannot pass, because it carries the old tag [tested]. Timeline of one apply,
from the audit log: planned 18:59:39 → built 19:00:16 → deployed 19:00:28 → verified 19:01:37 [tested].

For lock-out and safety state, read **live** messages only, not retained ones. That way a stopped PLC cannot
look safe; treat "nothing received" as "unsafe" [tested design].

## Rollback

If the build, the deploy or the verify fails, `plc.py` restores the source GVL and redeploys the backup from
step 5 [tested with a fake PLC in unit tests; not triggered on the real PLC]. A second approved change was
used as a real revert (111 s, read back `WeldCycle_ms = 55000.0`) [tested].

## Headless UI (only needed to create a skeleton)

Playwright + chromium-headless-shell against `c4-cli standalone-session --with-browser /tmp/fakebrowser.sh`
[tested]:

- Keep **one** page open for the whole session. A new browser on the same URL gets HTTP 403 (`docs/01`).
- The start page is an iframe from `startpagec4.codesys.com`, so look for links inside `page.frames`.
- Dialogs are Angular Material (`mat-dialog-container`). Fill `input`s by index and click the text
  `Create` / `OK`. In the Add PLC dialog, click the device name text, then fill the PLC name input.
- After each step, check the result on disk (`find <proj>`). The UI writes the files immediately.
- The UI showed `Library resolution failed: Failed to resolve all libraries for the project …/Application.iecapp. No Libraries.lock.json will be written.`
  right after Add Program. That was the repository path problem from step 0 [tested].
